# Vardha Voice Connect v1.1 — Final QA Check

## Scope

This release was reviewed against the supplied AI Voice Calling Agent assignment and the previous v2.3.5 project.

## Assignment flow checked

- Enter mobile number
- Place outbound call
- Exotel AgentStream WSS
- Gemini Live API speech-to-speech
- Natural AI introduction
- Knowledge Base answers only
- No guessing when information is missing
- Call recording
- Transcript
- Call summary
- Call history
- Duration and final status

## Main fixes in v1.1

### Deployment
- Added Render-ready Dockerfile.
- Daphne binds to `0.0.0.0`.
- Uses Render `PORT` with a safe `10000` fallback.
- Added `render.yaml`.
- Added PostgreSQL support through `DATABASE_URL`.
- Local development falls back to SQLite when `DATABASE_URL` is empty.
- Added WhiteNoise for production static files.
- Added secure proxy/HTTPS settings for Render.
- Render hostname is automatically used as the public base URL when `PUBLIC_BASE_URL` is empty.

### Voice bridge
- Exotel telephony is requested at 8 kHz.
- Gemini output PCM is 24 kHz.
- Stateful PCM resampling is used in both directions.
- Gemini is connected only after Exotel sends the `start` event.
- The greeting is sent only after `session.updated`.
- No test tone is generated by the application.
- Outbound media is buffered and paced.
- Exotel `streamSid`, chunk, timestamp and sequence number are included.
- Barge-in clears pending audio and cancels the active AI response.

### Call data
- Added database indexes for common history/KB queries.
- Active call history is lightly reconciled with Exotel.
- Call detail refreshes provider data.
- Recording is served through a backend proxy because provider recording URLs may require authentication.
- AI/bridge failures are stored as FAILED.
- Duration is calculated from answered time to end time.

### UI
- Version is 1.0.
- Application title is `Vardha Voice Connect — AI Voice Calling Agent`.
- Call history uses a clear table layout.
- Status, duration, recording state and summary are visible in the table.
- Call detail includes call outcome, transcript and the four summary areas requested by the assignment.
- Responsive layout remains available for desktop, tablet and phone widths.
- Simple developer-written wording is used throughout the interface.

## Static verification performed

- Python source parsed with `ast` successfully.
- Python files compiled successfully with `compileall`.
- `docker-entrypoint.sh` passed `sh -n` syntax validation.
- Render YAML parsed successfully.
- Required Docker/Render settings were checked.
- Old v2.3.x version strings were removed from the release files.
- `.env` contains no real API credentials and is ignored by Git.

## Runtime verification limitation

The current build environment does not provide Docker and cannot reach PyPI from the sandbox, so a real Docker image build and a live Exotel/Gemini call cannot be executed here.

The final live check must therefore be done after GitHub/Render deployment with the user's real Exotel and Gemini credentials. The software is designed to fail with a clear configuration message instead of placing a call when the public WSS endpoint or required credentials are missing.

## Important external dependency

A complete real call still depends on Exotel Connect Voice AI / AgentStream being enabled for the account, a valid ExoPhone/destination, and Gemini Live API access. These are provider-side requirements and cannot be verified from source code alone.


## v1.1 provider change
- Default AI provider: Gemini Live API.
- Live model: `gemini-3.1-flash-live-preview`.
- Summary model: `gemini-3.1-flash-lite`.
- Exotel 8 kHz PCM is resampled to Gemini 16 kHz input.
- Gemini 24 kHz PCM output is resampled back to the negotiated Exotel rate.
- Input and output audio transcription are enabled for call transcripts.
- Provider quota/key errors are converted into friendly call-detail errors.

This source package was statically checked in the build environment. A real phone call still requires the user's Exotel account, public WSS deployment, and a valid Gemini API key/quota; those external services cannot be proven by source inspection alone.


v1.1.1 targeted fix: The reported production error `You cannot call this from an async context - use a thread or sync_to_async.` was traced to `system_instructions()` reading `KnowledgeItem` synchronously inside the async Gemini WebSocket consumer. The Knowledge Base load is now executed with `sync_to_async`.

The assignment requirements were rechecked against the supplied PDF: outbound call, editable Knowledge Base, KB-only answering/no guessing, recording, transcript, four-part summary, call history, and the complete end-to-end flow are represented in the application. The end-to-end flow must still be validated with a real Exotel + Gemini call after deployment. Exotel trial/KYC destination restrictions remain provider-side and cannot be bypassed in code.
